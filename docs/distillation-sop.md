# 抖音博主视频蒸馏流水线（SOP）

> 用途：把一位短视频博主的全量口播/图文内容，蒸馏成结构化知识库（可用于 RAG、skill 外挂知识、微调语料备档）。
> 本文来自 super-official-writer 项目 7 位博主、700+ 期视频的实操沉淀（凌云笔杆子/惠水组工/公文摆渡/捉刀人/材料改稿室/大雨写材料/加夜班的文兄），流程经过 8 轮完整跑通与多轮返工修正——踩过的坑都写进去了。
> 目标读者：一个没有任何背景知识的执行窗口（AI agent），拿到本文 + 一条博主主页链接即可开工。

---

## 全流程总览

```
① 摸底(probe) → ② 下载(dl) → ③ 提音频+合并成批 → ④ 语音转写(人工上传) 
→ ⑤ 时间戳切分回单期 → ⑥ 逐期蒸馏成知识条目 → ⑦ 入库(jsonl+层文件+索引) → ⑧ 验收
```

**耗时参考**：220 期视频约 15 小时音频，全程约 1-2 个工作日（其中等待人工转写的时间不算）。

**铁律**（先记住三条，比流程更重要）：
1. **不编造**：转写文本缺什么就标"转写截断"，知识缺什么就如实留缺，绝不为完整性虚构内容。
2. **编号可溯源**：每条知识带博主编号（如 WX01、GC05），底稿留 220 期清单，任何一条能追回原始视频。
3. **素材库型内容合并蒸馏**：同系列多期合并为少数条目并注明覆盖期号，不一期一条硬凑数。

## 前置条件（一次性准备）

| 工具 | 用途 | 说明 |
|------|------|------|
| douyin-downloader | 下载视频/元数据 | 本项目用 `archive/tools/douyin-downloader/`（GitHub 开源 JoeanAmier/TikTokDownloader 同类皆可） |
| ffmpeg / ffprobe | 提音频、测时长、静音分隔、图转码 | 命令行工具 |
| 通义听悟（tingwu.aliyun.com） | 语音转写 | 网页版，人工上传合并后的批次音频；免费额度足够 |
| 可识图 AI（如 vision-reader 子代理） | 图文期识读 | 仅当博主有图文内容时需要；WebP 需先转码为 JPEG |

## 第 ① 步：摸底（probe 模式）

目的：只拉元数据不下载视频，搞清三件事——**博主是谁、多少期、视频还是图文**。

1. 解析分享短链拿到主页链接：
   ```bash
   curl -sL -o /dev/null -w "%{url_effective}" "https://v.douyin.com/xxxx/"
   ```
   跳转目标里的 `sec_uid=MS4wLjAB...` 就是博主唯一标识。
2. **查重**：拿 sec_uid 对比已蒸馏博主库（我们的库记在 `lingyun/*/download_manifest.jsonl` 的 `author_sec_uid` 字段）。已蒸馏过就直接结束。
3. 写 probe 配置（`video:false, json:true`）跑一遍，产出 `download_manifest.jsonl`（每期一行：日期/aweme_id/标题/时长）。数一下期数、看标题风格，判断内容密度与蒸馏价值。
4. 按期数规划批次（见第 ③ 步）。

```yaml
# probe 配置要点（完整模板见 config_b5_probe.yml）
link:
- https://www.douyin.com/user/MS4wLjAB....   # 主页链接
path: F:/工作区/bloggerN/                      # 每位博主独立目录
video: false      # probe 不下视频
json: true        # 只要元数据
mode: [post]
```

> 坑：cookies 会过期。下载失败先检查 cookies（浏览器登录抖音后从 devtools 拷贝），工具自带 cookie_fetcher 可半自动刷新。

## 第 ② 步：下载（dl 模式）

复制 probe 配置，把 `video: true`，只加 `music/cover` 按需（一般 false），跑一遍下载全部视频。产出：`博主名/post/` 下按期存放的 mp4 + 每期 json。

> 坑：视频文件很占空间（220 期约 2-4 GB）。**蒸馏完成并验收后立即删除视频**，只留 json 元数据与转写文本——我们是知识库项目不是视频收藏项目。

## 第 ③ 步：提音频 + 合并成批

目的：通义听悟逐个上传太慢，把全部音频合并成 3-5 个批次文件，一次传一个。

```python
# 每期：ffmpeg 提音频（16kHz 单声道 64kbps mp3，转写够用且省空间）
ffmpeg -y -i 视频.mp4 -vn -ac 1 -ar 16000 -c:a libmp3lame -b:a 64k 期次.mp3
# 批间：每期之间插入 3 秒静音（听悟按静音断句，切分回单期全靠它）
# 每批控制在 4.5 小时以内（听悟单文件时长上限的稳妥值）
```

关键产物：`mapping.json`——**按顺序记录每个片段属于哪一期视频、起止时间**，第 ⑤ 步切分全靠它。

> 坑（吃过亏）：合批前先用 ffprobe 逐个测时长记入 mapping；批次不要超过 5 小时。

## 第 ④ 步：语音转写（人工环节）

**这一步让人做，AI 只负责告诉人传哪些文件**：

1. 告诉用户：批次文件在哪个目录（如 `lingyun/bloggerN/batches/batch1.mp3`），共几批。
2. 用户上传到通义听悟网页版 → 转写 → 导出"笔记"或"原文"（带时间戳的 markdown）。
3. 用户把导出文件放进 `bloggerN/transcripts/`，说一声"好了"。
4. AI 检查文件里的时间戳格式，确认能解析。

> 为什么人工：听悟需要账号登录且网页操作，自动化得不偿失；批量合并后人工成本只剩"上传×N+导出×N"。

## 第 ⑤ 步：时间戳切分回单期

写脚本（模板 `archive/tools/split_transcripts.py`）：

1. 解析转写 markdown 里的时间戳段落（听悟格式：`发言人 H:MM:SS` 行 + 正文段）。
2. 按 mapping.json 的每期起止时间把段落归位到对应视频；
3. **容差规则**：切分点 ±2 秒内取最近段落边界；某期一个段落都没匹配上（转写漏段），放宽到 ±10 秒再找；还找不到就标注"转写缺失"。
4. 产出 `per_video/日期_标题.md` 一期一文件（220 期 → 220 个文件）。

**图文学期（如有）**：走另一条线——gallery 图片批量 `ffmpeg -i xxx.webp scale=1200:-1 -q:v 2 xxx.jpg` 转码后交给识图 AI，按期合并成文字稿放进同一个 per_video 目录。

> 坑：WebP 不转码直接喂识图 API 会超预算报错；转码时压到宽 1200 以内。

## 第 ⑥ 步：逐期蒸馏成知识条目（核心）

这是唯一需要"智能"的步骤。给执行 AI 的蒸馏指令要点：

**输入**：per_video/ 全部单期文稿 + 每期标题日期。
**产出**：一份"蒸馏底稿"（markdown），格式：

```markdown
# 蒸馏底稿·博主名（N 期）

> 来源：抖音博主"XXX"N 期视频蒸馏（起止日期）。特色：一句话概括博主的知识类型。
> 转写错别字已按语义修复（举例）；营销语一律不录（"点赞收藏""评论区留言"等）。

## N 期清单（溯源底账）
2024 年 11 月（3 期）：27 标题A｜28 标题B｜30 标题C
（全部期号列出，一期不落——这是审计依据）

## 一、分类主题（如：句式模板）

### G01 条目标题（提炼方法名/框架名）
①**框架/句式**（解释+适用场景）；②**...**（同款教学型每期一条或同系列合并）
→ 主题归属（如"词句升级"）

### G02 ...
```

蒸馏规则（按优先级）：
1. **一期一条**教学型内容（讲一个框架/方法）→ 提炼成"名称+框架+适用场景"，保留博主原句式示例（加粗），不掺自己的话。
2. **素材库型内容**（句式合集、金句合集、多期同系列）→ **多期合并为一条**，条目内注明"覆盖第 X-Y 期"。
3. **转写修正**：按语义修复错别字（"啃硬骨头"不写成"啃 Ying 骨头"）；转写残留的英文/乱码剔除；**博主口播营销尾巴一律不录**。
4. **截断如实**：某期转写首句缺失，条目照写但标"（转写截断）"。
5. **条目尾统一 `→ 主题`**，为主题归类字段做准备。
6. **数量预期**：教学型博主约 0.4-1.2 条/期；素材库型合并后更少。220 期出 200+ 条正常，55 期出 80 条也正常——密度由内容决定，不凑数。

**验收**（蒸馏完自查）：清单期数=实际期数；随机抽 10 条能从 per_video 原文找到对应内容；无营销语残留。

## 第 ⑦ 步：入库（三层结构）

我们项目的存储哲学：**存储按来源、检索按知识**。

```
① 层文件（知识正文）：blogger-<博主名拼音>.md，按主题分节，每节开头写覆盖说明
② 结构化数据集：dataset.jsonl 追加，每条一行 JSON：
   {"id": "博主缩写_编号", "source": "博主名", "batch": "v版本号",
    "video_span": "期号/日期", "title": "条目标题",
    "category": "主题", "category_raw": "原始主题词", "content": "正文"}
③ 索引：INDEX.md 由脚本从 jsonl 自动生成（id｜标题｜层文件 三列），勿手改
```

- id 编号体系要唯一（我们用：WX=文兄、GC=改稿室、DY=大雨、G=公文摆渡……新增博主先查前缀占用）。
- 层文件头部写"查重说明"：新条目与既有库哪些条目重叠、为何保留（差异化角度）——这个说明日后比条目本身还有用。
- 跑索引脚本重生成，数字承诺抽检（标题说"6 个"正文就得有 6 点）。

## 第 ⑧ 步：验收与收尾

1. dataset 无重复 id、条数对账（旧数+新条=新总数）。
2. 层文件头部计数与实际条目数一致。
3. INDEX 重生成后 diff 只含新增行。
4. **删除已验收的视频文件**（保留 json 元数据）。
5. 把蒸馏过程写进版本 CHANGELOG（新增博主名/期数/条数/特色一句话）。

## 附：适配其他领域的修改要点（如"财务 ERP"博主）

流程 ①-⑤ 完全通用；⑥⑦ 的**主题分类体系**需要按领域重建。给财务领域预置一组分类供参考：

- **业务概念**（凭证/科目/结转/对账的业务含义）
- **操作路径**（软件操作步骤、界面路径——ERP 博主的重要内容，建议保留博主原话的菜单位置）
- **实务经验/坑**（月末结账顺序、跨期陷阱、常见对账不平原因）
- **规范口径**（会计准则条款、税法口径——注意时效，条目标注适用年份）
- **场景解法**（某行业/某业务的完整配置思路，教学型一期一条）

蒸馏规则不变：不编造、编号可溯源、素材库合并、截断如实。对 ERP 开发者来说，**"实务经验/坑"和"操作路径"两类条目价值最高**——前者告诉你软件要防什么错，后者告诉你用户的心智模型（用户在哪个界面找什么功能）。

## 附：常见故障

| 症状 | 原因 | 处理 |
|------|------|------|
| 下载 0 个视频 | cookies 过期 | 刷新 cookie 重跑 |
| 听悟转写某批全空 | 批次文件超时长上限 | 拆批重合并 |
| 切分 miss 很多 | 静音间隔不足/转写质量差 | 检查合并时是否真插了 3 秒静音；miss 放宽 ±10s |
| 识图 API 报错超预算 | WebP 未转码/分辨率过高 | ffmpeg 转码 scale=1200:-1 |
| jsonl 追加后 id 冲突 | 新博主前缀与旧编号重叠 | 入库前全库查重 |
